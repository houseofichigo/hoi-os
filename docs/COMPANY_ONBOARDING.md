# Company and team onboarding

`hoi-company-onboarding` prepares a shared operating foundation from selected existing work. `hoi-onboard` configures the engine workspace and guides actual intake. Use either when it fits; document preparation does not require the user to finish runtime setup first.

## Modes

| Mode    | Evidence                                                             | Output                                                    | Reviewer                                      |
| ------- | -------------------------------------------------------------------- | --------------------------------------------------------- | --------------------------------------------- |
| Company | Selected existing company documents, conversations and owner answers | Reconciled operating documents; optional 19-file baseline | Owner or delegated coordinator                |
| Member  | Shared reviewed foundation, member examples and answers              | One concise role/workflow profile                         | Member, plus responsible lead for assignments |
| Client  | Selected relationship context, guidelines and active brief           | Shared client context and engagement brief                | Account and delivery owners                   |

Read the relevant skill references. First make a coverage table of supported answers, exact sources, conflicting/missing topics and destination documents. Draft supported material, then ask only unresolved questions. Voice and text use the same confirmation process. Existing chat usage does not imply access to a whole account; use material actually provided or explicitly selected through available tools.

## Document ownership

The 19-file baseline is human-readable company context. Reconcile existing locations and review states. In an installed workspace, inspect managed manuals before choosing output paths; do not overwrite adapter blocks or create parallel engine state. Business goals and filing records may describe reviewed decisions and receipts but do not replace onboarding, source identity, approval or schedule records. Draft presence does not mean onboarding is complete.

Keep originals and prior versions. Distinguish reported, inferred, confirmed, conflicting, missing and deferred information. Retain written review and ask for the decisions needed to make the next workflow useful. A member's preferences do not redefine company-wide responsibilities.

## Distribution

The bundled package uses the product namespace `hoi-company-onboarding`. It is adapted from the neutral `company-harness-onboarding` instructions, with a product-specific handoff and managed-manual ownership guidance. Required engine operations and optional connections are empty: document/interview preparation itself invokes no new API. The product's existing catalogue uses the operational instruction category and distributes it through Codex/Claude adapter mirrors and the skill collection archive.

Updating this source checkout does not update an installed private runtime, install anything in a user's ChatGPT account or publish a release. Use supported version adoption and adapter updates separately.

## Validation

The [fictional review scenarios](../examples/company-onboarding/README.md) cover existing answers, ambiguous shared-account authorship, conflicting evidence and missing decisions. They are review material, not measured live model performance.

The automated suite checks package completeness and byte parity, catalogue compatibility, and installation/resolution of all supporting references in an isolated fictional workspace for both adapters. Live interviews, fresh host discovery and usability still need explicit observation. No client transcript, completed client documents or private runtime data is included.
